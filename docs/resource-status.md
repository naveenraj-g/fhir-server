# FHIR Resource Status

The single record of which FHIR R4 resources are built on the current architecture, what each one serves, and what is still open. **Update it in the same commit as any change to a resource** (see [Keeping this file current](#keeping-this-file-current)).

_Last updated: 2026-11-23, after rebuilding MedicationDispense._

## Architecture in one line

Medplum-style: the whole FHIR R4 resource lives in one `content` JSONB column; only the elements a search parameter filters on are indexed into columns and child tables (derived from `content` on every write). One `SearchRegistry` per resource. FHIR R4 JSON in and out. Direct JWT/RBAC auth. One-way migrations. Details: `CLAUDE.md` ("Medplum-style storage") and `.claude/commands/new-fhir-resource.md`.

### Required-binding codes and HL7 alignment (checked by a test)

A search parameter that reads a `code` element with a **required** binding is held in a Postgres enum (`ARRAY` of the enum for 0..*, a column on the child row when the element is nested); extensible/preferred/example codes and CodeableConcepts stay strings in token tables. `tests/unit/test_hl7_alignment.py` reads HL7's own R4 package (4.0.1) and, for all 32 rebuilt resources, checks that the registry serves exactly the parameters (and parameter types) HL7 lists, and that every required-binding `code` parameter is an enum column (`REQUIRED_CODE_STORAGE` lists them; a new resource must add its own). Commit `bfc7873`. Fixed by this audit: AllergyIntolerance `category` / `reaction.severity` and Appointment `participant.status` (migration `a1d7e4f0b826`, verified on a scratch DB with old-shape rows); also `b3f9a6c2d741` adds indexes the early rebuild migrations missed (Condition, RelatedPerson, AllergyIntolerance, FamilyMemberHistory, RiskAssessment, Patient). `scripts/audit_hl7_live.py` does the same against the live hl7.org R4 files (names, types, reference targets, enums vs value sets, no stray enums); last run: all 32 clean, with the notes that R4 also lists `Group` as a target of `patient` and `EpisodeOfCare` as a target of `encounter` on several resources (ours narrows `patient` to Patients; EpisodeOfCare is not rebuilt yet). HL7's package also defines parameters on *extensions* (Patient `mothersMaidenName`, Observation `gene-*`, ...); they are not on the resource pages and are intentionally not served.

### Write-time reference check (one shared rule for every rebuilt resource)

There is no per-resource list any more. On every create and patch, `app/repository/_reference_check.py` walks the
stored FHIR document and checks **every** relative `Type/<id>` reference, wherever it sits (nested backbone elements,
`identifier.assigner`, note authors, extensions, contained resources):

| Reference | What happens |
|---|---|
| relative `Type/<id>` of a **rebuilt** resource (the `RESOURCE_REGISTRY` types with a content-based model) | must exist in the caller's org, otherwise **422** naming the element (`activity[1].detail.performer[0]: referenced CareTeam/999999 does not exist`) |
| absolute URL, `#contained`, only `identifier` / `type` / `display`, or a type this server does not have (Goal, Task, Device, ... — the registry also still lists old, not-yet-rebuilt resources whose routes are off) | stored as sent |
| right type for the element? (`Observation/1` in `CarePlan.subject`) | **not checked here** — the `java_validator` backend rejects it; the native JSON-schema check (and so the Java fallback) does not |

Registering a rebuilt resource in `RESOURCE_REGISTRY` is all it takes for every other resource to check references to it.
Covered by `tests/unit/test_reference_check.py` and `tests/integration/reference_check/` (one row per rebuilt resource in
`cases.py`, a dangling reference to every checkable type on every resource).

## Keeping this file current

Update this file **in the same commit** whenever you:

- **rebuild or add a resource**: add its row to section 1 (route, params, sequence, migration revision, commit hash once known), remove it from section 2, and fill its row in the existence-check table;
- **wire one resource to another** (a new existence check, include or chain): edit the affected rows' "Checked" and "Stored as sent" cells, and close the matching item in section 3;
- **add an engine capability** (a new search type, modifier or helper): add a row to section 4 and, if it closes a gap, remove it from section 3;
- **find or close a known gap**: edit section 3;
- **change the route prefix, sequence block or parameter count** of a resource.

Then bump the "Last updated" line. Verify the parameter count with:

```bash
uv run python -c "from app.fhir.capability import SEARCH_REGISTRIES as R; print({k: len(list(f().params.values())) - 2 for k, f in R.items()})"
```
(each registry includes `_id` and `_lastUpdated`, hence the `- 2`), and the mounted list with `configs/config.yaml` → `routes.enabled`.
