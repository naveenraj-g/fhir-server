FHIR Server Search Architecture

How our fhir-server answers a FHIR R4 search for Organization and Location: the request path, how a query string is parsed, the registry that drives everything, how a parameter becomes SQL, how the index is kept in step on writes, and what the result Bundle contains. Both resources run on the same engine; only their registry differs.

Organization · Location FastAPI · SQLAlchemy async · PostgreSQL FHIR R4 search
engine component data store request / data in response / data out error

From HTTP request to searchset Bundle

Five layers, each doing one job. The tenant (the caller's org_id) is fixed at the dependency layer and then carried to the SQL, so a search can never leave the caller's organisation.

Parsing: how a query string becomes a SearchRequest

parse_search looks at each (name, value) pair in order and sends it down the first rule that fits. Result parameters fill the request directly; search parameters become clauses.

One declaration, three consumers

A resource declares its parameters once as a SearchRegistry of SearchParam entries. Each field below is read by the stages that dots mark, so what the OpenAPI page documents is exactly what the parser accepts and the SQL runs.

From SearchRequest to SQL

Each clause is turned into one SQL condition by the builder for its parameter type. The conditions are ANDed with the tenant filter; the rest of the request decides ordering, paging, the count and the includes.

The write side keeps the index in step

Search never reads the FHIR document to decide a match. It filters on columns and child tables derived from the document on every write. The document itself is only read to render the response.

The searchset Bundle

What searchset_bundle assembles: a total, paging links, and entries of three kinds. The three entry kinds are told apart by entry.search.mode.

What the engine supports

The same facts as the figures, as a reference. Organization and Location share the engine; the two registries are listed separately below.

Result and control parameters

ParameterBehaviour
_countPage size. Default 50, capped at 200 (pagination.default_limit, max_limit). 0 returns only the total.
_offsetMatches to skip (not in the FHIR spec; the paging links carry it).
_sortComma list, - for descending. Only parameters with a sort key; an unknown name is a 400, an unsortable one is "not supported". _score is refused.
_totalnone skips the count, estimate and accurate both count exactly. Default accurate.
_summarytrue, text, data, count, false. text cannot be combined with _include or _revinclude.
_elementsComma list of top-level elements; applied to match entries; the resource is tagged SUBSETTED.
_include, _revincludeOnly the targets the registry declares, with :iterate (up to 10 rounds). Declared, but adding nothing: Endpoint, which is not stored on this server.
_contained, _containedTypeAccepted only as false and container; anything else is "not supported".
_format, _pretty_format must be a JSON form, else 400; _pretty is accepted and has no effect.
Prefer: handling=strictUnknown and unimplemented parameters become a 400 instead of being ignored.

Common parameters and mechanics

ItemBehaviour
_idToken. :not, :missing. Sortable.
_lastUpdatedDate, all nine prefixes, precision-aware ranges. :missing. Sortable.
_tag _profile _security _source _text _content _list _has _type _filterNot implemented: ignored with an outcome entry (400 under strict).
_queryAlways a 400, even in lenient mode.
Modifiers by typestring: :exact :contains :missing · token: :text :not :above :below :in :not-in :of-type :missing · reference: :identifier :above :below :missing and :Type · date: :missing. Each parameter lists the subset it really supports.
OR / ANDComma is OR; repeating a parameter is AND; different parameters are ANDed.
ChainingOrganization partof → Organization; Location organization → Organization and partof → Location. Recursive. No reverse chaining (_has).
EscapingA literal , | $ \ is written with a leading backslash.
POST /_searchSame parameters form-encoded in the body; query-string parameters are combined with it.
