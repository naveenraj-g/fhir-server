# Data modeling for an AI-native EMR/EHR

This project isn't just a native EMR with a FHIR export layer bolted on — per `CLAUDE.md`'s "OpenAPI Spec = MCP Contract" section, every endpoint is also exposed as an AI tool via a FastMCP server, and field/route summary strings exist specifically so an LLM can understand what a tool does. `app/models/terminology/terminology.py` carries synonym/translation/**embedding** columns for semantic concept search — further evidence AI consumption was a first-class design goal, not an afterthought. That has two consequences worth calling out separately from the general native-EMR case in `storage-strategies.md`.

## 1. Granular, typed, normalized data serves an AI agent *better* than a document blob

For a human-facing UI, either storage model can be made to work — the UI layer smooths over a lot. For an AI agent calling your API as an MCP tool, the interface quality matters much more directly, because the agent has no rendered screen to sanity-check against, only the schema and field descriptions you give it:

- A flat, typed field (`status = "active"`) is something an agent can filter, compare, and reason over reliably. A JSON blob requires the agent to parse nested structure correctly every time, with more surface area for it to hallucinate a field name or path that doesn't exist.
- Coded values (`code`/`system` pairs from a `CodeableConcept`, flattened as this project already does) let an agent match against a known vocabulary instead of doing fuzzy reasoning over free text — this is exactly why the `terminology` service's embeddings/synonym matching exists: to bridge natural-language agent queries onto the same controlled, structured codes the rest of the schema uses.
- The dual response format (`application/json` snake_case vs `application/fhir+json`) is itself an AI-ergonomics decision: deeply nested camelCase FHIR JSON is harder for an LLM to reliably produce/consume in a tool call than a flatter snake_case shape.

**Conclusion:** the granular relational model is, if anything, more clearly the right call for an AI-native system than for a purely human-facing one. Nothing about "AI-native" argues for a document store here.

## 2. But spec-fidelity bugs are more dangerous with an autonomous consumer

This is the part that needs new emphasis. When a clinician looks at a chart and something reads oddly (an unfamiliar status code, a missing field), they usually notice and route around it using judgment and context an LLM tool-caller doesn't reliably have. When an agent calls `GET /encounter/{id}` and gets back `status: "on-hold"` — a real R5 code that shouldn't exist in this R4 system, per the [model audit](../test/models-fhir-r4-audit.md) — it has no independent way to know that's wrong. It will reason and potentially act on bad data with the same confidence as good data. This raises the priority (not the novelty) of a few things already in `production-readiness-checklist.md`, plus two new ones specific to the AI-tool surface:

- **Automated conformance testing (checklist item 1) is now the highest-priority item in the whole audit, not just the highest-leverage one.** It's the difference between a wrong code being caught in CI versus being caught only when an autonomous agent has already acted on it.
- **MCP-facing field/route descriptions must stay accurate over time.** They aren't just documentation — per `CLAUDE.md`, they're the LLM's *only* source of truth for what a field means. A stale or misleading `summary`/`description` string is a silent MCP-contract bug in the same category as the schema-drift bugs the audit found, and should be checked the same way (`/openapi.json` verification is already called out in `CLAUDE.md` as required after any schema change — treat that as covering this too).
- **Audit/provenance trails become load-bearing, not optional, once writes can be AI-initiated.** This project already has `AuditEvent` and `Provenance` resources modeled — good — but as MCP tools start performing writes (create/update), `created_by`/`updated_by` and Provenance/AuditEvent entries need to reliably distinguish an agent-initiated action from a human one, so a bad write can be traced and, if needed, attributed and rolled back. Verify this distinction is actually captured (e.g. does `request.state.user.get("sub")` differ meaningfully when the caller is an MCP tool invocation vs. a human session?) rather than assumed.
- **Consider a stricter validation gate on AI-initiated writes than human ones**, at least while confidence is being built — e.g. requiring a narrower, more constrained write schema for MCP-driven creates/updates than the full API surface allows for human-driven ones, or flagging agent-created resources for review. This isn't a data-*modeling* change so much as a policy one, but it follows directly from point 2 above and is worth deciding deliberately rather than by default.

## Net effect on the recommendation

Nothing here changes the storage-model recommendation in `storage-strategies.md` — normalized relational is still correct, arguably more so. What it does is move automated spec-conformance testing and MCP-contract accuracy from "good hygiene" to "the load-bearing safety mechanism for an autonomous consumer that has no other way to catch a wrong value," and adds agent-vs-human write provenance as a concrete new checklist item.
